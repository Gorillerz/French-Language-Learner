# ADR 0001: V1 client-first architecture

The V1 spec (#11) sets product behaviour but names no stack. The app is a private, single-Learner PWA whose data must be readable only on the Learner's devices, so we build a client-first app in which every feature works against local storage, and the cloud only ever holds ciphertext.

## Decisions

- **Client**: TypeScript (strict), React, Vite, and `vite-plugin-pwa` for the manifest and service worker. Plain CSS. No client-side router dependency unless a ticket needs one.
- **Local store**: IndexedDB through Dexie. It is the source of truth for the UI. Every user-editable or synced row carries a stable id and a `savedAt` timestamp, so that #17 can add sync without reshaping data.
- **Built-in content**: curated vocabulary, grammar, and questions ship as typed data in the bundle. Learner-editable content (vocabulary) is seeded into the local store on first run, with `savedAt` at the epoch so any Learner edit wins. Read-only content (grammar, curated questions) stays in the bundle and does not sync. Built-in ids are stable across devices.
- **Testing**: Playwright is the one test seam. Tests drive Learner-visible behaviour against the production build served locally, with controlled stand-ins for cloud sync and AI. Vitest is used only for deep pure logic, such as review priority and crypto, and for built-in content integrity, where browser tests would be a poor fit.
- **Service configuration**: the app reads the cloud and AI base URLs from build-time config, so tests can point them at stand-ins. A cloud URL that is neither HTTPS nor loopback is refused, which switches sync off.
- **Encryption**: WebCrypto only. A random data key encrypts each record with AES-GCM. That data key is wrapped twice, by keys derived from the passphrase and from the recovery code (PBKDF2-SHA-256, at least 600,000 iterations, per-wrap random salt). The wrapped key bundle is stored in the cloud so a second device needs only the passphrase. Plaintext keys and passphrases never leave the device. A device keeps its keys as non-extractable CryptoKeys in IndexedDB, so it is unlocked once and offline study never needs the passphrase. The local store stays readable on the device. The recovery code holds 160 bits from the CSPRNG. Recovery rewraps the data key under a new passphrase and leaves it unchanged. A second random key, carried in the bundle under the data key, turns row ids into opaque record ids, because built-in row ids contain readable French.
- **Sync**: record-level encrypted blobs over a small provider-neutral HTTPS contract, `docs/sync-contract.md` (sign-in, key bundle, push, pull since cursor). The cloud sees opaque record ids, a monotonic server cursor, and ciphertext. Conflicts resolve on the client, most recent `savedAt` wins, with the row's canonical JSON breaking a tie. Deletions sync as tombstones. Setup is optional and sits in its own area, so the app never waits for it. What needs pushing is derived rather than queued: a row is dirty when its `savedAt` differs from the one the cloud is known to hold, so it survives closing the app and covers data from before setup. A table joins sync by being listed in `syncedTables`. Sign-in is an ordinary account, separate from the passphrase; the two may not be equal, because the host receives the sign-in password.
- **AI**: direct HTTPS from the browser to OpenRouter's chat completions API, using a Learner-supplied API key held in encrypted settings. There is no AI proxy to host. Every call sits behind one module that takes an explicit Learner action and a minimal payload.

## Consequences

- No specific cloud host is chosen. The sync contract is implemented by the test stand-in, `e2e/support/cloud-stand-in.ts`; pointing a real deployment at it is a separate decision.
- Each device pays a PBKDF2 unlock cost, which is acceptable for a passphrase entered rarely.
- Finding dirty rows scans every synced table each cycle. That is fine at this scale, but a table of very many rows would need an index.
- There is no server push: a device polls every 30 seconds, and on reconnecting or being reopened. The same calls tell the app whether the cloud can really be reached, so the connection only reflects the cloud once sync is set up. Before that it follows `navigator.onLine`.
- Timestamps come from device clocks, so most-recent-save can misorder edits under clock skew. That is accepted for a single Learner.
